## 2. Поднятые сервисы

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище файлов Iceberg | Позволяет локально использовать S3 API для Spark и Trino. MinIO собран из официальных исходников релиза 2025-10-15. |
| PostgreSQL 16.6 | БД для служебных данных Lakekeeper | Поддерживается Lakekeeper и сохраняет состояние каталога между перезапусками. |
| Lakekeeper 0.10.0 | Iceberg REST Catalog — каталог метаданных таблиц | Предоставляет единый REST-каталог для Spark и Trino без отдельного Hive Metastore. |
| Trino 484 | SQL-движок для загрузки TPC-H и выполнения Q3 | Имеет готовый генератор TPC-H и поддерживает чтение и запись Iceberg через REST-каталог. |
| Spark 3.5.6 | Обработка данных Bronze, построение Silver и Gold | Подходит для пакетных преобразований, проверки качества данных и работы со снапшотами Iceberg. |

### Скрипты, которыми поднимал стек

Команды Docker Compose из скрипта запуска:

```powershell
docker compose build minio bucket-init runner spark
# Собирает MinIO и образы для создания bucket и выполнения заданий.

docker compose up -d --wait postgres minio lakekeeper trino
# Запускает PostgreSQL, MinIO, Lakekeeper и Trino с настройками из compose.yaml.
# Данные хранятся в именованных томах; порты сервисов: 9000/9001, 8181 и 8080.

docker compose run --rm runner bootstrap

```

## 3. Разбор запроса — какие данные нужны

Какие таблицы и колонки TPC-H реально нужны запросу.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает |
|---|---|---|
| customer | custkey, mktsegment | Фильтр по сегменту BUILDING и соединение с orders. |
| orders | orderkey, custkey, orderdate, shippriority | Соединения с customer и lineitem, фильтр orderdate < 15.03.1995, вывод даты и приоритета. |
| lineitem | orderkey, extendedprice, discount, shipdate | Соединение с orders, фильтр shipdate > 15.03.1995 и расчёт выручки extendedprice × (1 − discount). |

## 5. Тесты производительности

Выполнил Q3 на копиях Bronze со сжатием GZIP и ZSTD в формате Parquet. Для каждого кодека записал три таблицы, выполнил первый запрос и три повторных. В таблице приведена медиана трёх повторных запросов и суммарный размер файлов данных соответствующей копии Bronze. Все ответы совпали с эталоном.

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | 46,338 с | 9 863,170 | Меньший размер данных; подходит, если важнее экономия места. |
| ZSTD | 44,850 с | 10 144,440 | Немного меньшее время Q3 в этом опыте и значительно более быстрая запись. |

Вывод: GZIP занял примерно на 2,8% меньше места. Суммарное время записи трёх таблиц составило 725,346 с для GZIP и 168,691 с для ZSTD: ZSTD записался примерно в 4,3 раза быстрее. По одному прогону записи нельзя оценить устойчивость этой разницы. Время Q3 оказалось близким: диапазоны повторных запусков пересекаются, поэтому устойчивое преимущество чтения не установлено.

Первый запрос занял 50,794 с с GZIP и 42,598 с с ZSTD. Кэши ОС и MinIO не очищались, поэтому эти запуски не считаются холодными. Все варианты выполнялись последовательно с одинаковыми настройками Trino.

При отдельном опыте с метаданными уплотнение customer уменьшило число активных файлов с 16 до 2, но не ускорило агрегацию: медиана изменилась с 0,166 до 0,191 с. Физический объём вырос из-за сохранённых старых снапшотов.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Lakehouse позволяет хранить большие объёмы исходных и обработанных данных в объектном хранилище и подключать разные вычислительные движки. Iceberg добавляет согласованные снапшоты и изменение схемы. Для небольшой транзакционной задачи обычная БД проще; Lakehouse полезен для масштабной аналитики и совместной работы нескольких движков. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | На отдельной копии 100 строк Silver выполнил `ALTER TABLE lake.demo_20261017t081928610866z.silver_evolution ADD COLUMN processing_note STRING`, затем переименовал processing_note в quality_note. Iceberg обновил схему без перезаписи старых файлов; у старых строк в новой колонке NULL. |
| Пример скрипта восстановления данных из снапшота (time travel) | В Spark SQL список снапшотов: `SELECT snapshot_id, committed_at FROM lake.demo_20261017t081928610866z.silver_evolution.snapshots`. Восстановление: `CALL lake.system.rollback_to_snapshot(table => 'demo_20261017t081928610866z.silver_evolution', snapshot_id => 6304754508904915203)`. После вставки стало 101 строка; историческое чтение и rollback вернули 100 строк. |

### 6.2. Подключить инструмент к lakehouse

Подключил Spark в Docker к общему каталогу Iceberg и показал чтение данных на **Bronze**-слое.

| Инструмент | Почему выбрал именно его |
|---|---|
| Spark | Выполняет очистку, соединения и агрегации, читает таблицы Iceberg из MinIO и поддерживает изменение схемы и восстановление снапшотов. |

**Подключение к lakehouse и просмотр данных:**

В задании настроен каталог `lake`: тип REST, адрес `http://lakekeeper:8181/catalog`, warehouse `practical1`, S3 endpoint `http://minio:9000`. Spark читает `lake.bronze_sf50.customer`, `orders` и `lineitem`. По пять записей каждой таблицы сохранены в [результате чтения Bronze](results/submission/spark-20261017T082813881847Z/spark-bronze-samples.json). Затем Spark выполняет преобразования и выводит Gold. Результат Gold совпал с исходным Q3 в Trino.

## 7. Выводы

В ходе практики я развернул Lakehouse на MinIO, PostgreSQL, Lakekeeper, Trino и Spark, построил слои Bronze — Silver — Gold и выполнил запрос Q3 на масштабе sf50.

Медальонная архитектура разделяет исходные данные, преобразования и аналитическую витрину. Из 300 005 811 строк lineitem после фильтров и соединений получено 1 496 692 строки Silver, а в Gold — десять заказов с наибольшей выручкой.

Общий каталог Iceberg позволил Spark и Trino работать с одними таблицами. Добавление колонки не потребовало перезаписи файлов, а снапшот позволил восстановить таблицу после изменения.

Я сравнил GZIP и ZSTD на Bronze. GZIP оказался компактнее, ZSTD значительно быстрее записался; время Q3 получилось близким. Для слоёв выбран Parquet с ZSTD как подходящий для этого опыта компромисс размера и скорости записи.

Кэширование и метаданные влияют на время запросов, поэтому сравнивать нужно при одинаковых настройках. Уменьшение числа файлов само по себе не гарантировало ускорения, а сохранённые снапшоты продолжили занимать место.
